## 一、项目最终目标

将现有的 Windows 摄影边框与水印工具 LumaCraft 扩展为支持 Android 的跨平台应用。

**Android 不是 Windows 的完整移植版，而是共享相同处理核心的移动端精简版。**

Windows 继续提供完整的预设设计和组件布局能力；Android 负责照片选择、预设应用、非结构性属性编辑、逐张文字修改和批量导出。

### 目标架构（概念示意）

```text
             LumaCraft 共享核心
    预设模型 / 字体 / 渲染规则 / EXIF / 导出
                    │
          ┌─────────┴──────────┐
          ▼                    ▼
      Windows UI            Android UI
   完整编辑器与图层管理    轻量编辑与移动端导出
```

项目遵循四项核心约束：

1. **共享核心**：继续使用同一个 Flutter 工程，避免维护两套照片处理逻辑。
2. **保护 Windows**：共享代码的修改必须通过回归测试，已经稳定的模块可以分阶段合并。
3. **兼容优先**：预设格式、字体资源、渲染规则和导出行为尽量与 Windows 保持一致。
4. **渐进开发**：先审查实际代码结构，再逐模块改造，经过 Alpha、Beta 验证后发布 Android v1.0。

## 三、仓库初步审查结果

上一轮审查涉及公开 README、`AGENTS.md`、项目台账以及部分关键 Dart 源文件。

**审查范围限制：** 未完整克隆仓库，也未执行 Flutter 构建或自动化测试。因此以下内容是上一轮的初步结论，具体实现仍需在 P0 阶段复核。

### 3.1 已检查的主要模块

| 路径 | 作用 |
|---|---|
| `app/lib/main.dart` | Windows 工作台入口，集中管理照片、预设、导出等状态 |
| `app/lib/editor/` | 预设数据模型、组件和图像渲染 |
| `app/lib/export/` | 尺寸、格式、命名、导出任务与色彩处理 |
| `app/lib/photo_state.dart` | 照片状态、EXIF 读取与部分格式判断 |
| `app/lib/ui/` | Windows UI、预设管理、地图及设置界面 |
| `app/lib/settings/` | 配置、地图服务和高德 JS API 支持 |

上一轮发现的主要架构问题是：`main.dart` 中的 `Workshop` 管理了较多桌面 UI 与业务状态，部分导出及持久化逻辑直接依赖文件路径。Android 不宜直接套用 Windows 工作台，而应逐步把共享业务逻辑从桌面界面中分离。

### 3.2 四项重要技术风险

#### 1. HEIC 支持不能直接照搬

Windows 版依赖 Windows 系统的 HEIC 解码能力。Android 虽然也具备相关解码能力，但仍须单独验证图片解码、EXIF、方向以及色彩转换结果，不能仅复制 Windows 实现。

#### 2. 高德地图需要平台适配

目前使用 Windows 专属 WebView 插件，并通过本机 HTTP 服务加载高德 JS 页面。

上一轮审查指出，现有实现要求用户配置高德 Key 和安全密钥。Android 应尽可能保留相同的配置与业务规则，但须验证 Android WebView、页面来源以及 JavaScript 通信。

#### 3. 导出文件的写入方式必须调整

Windows 导出任务使用文件路径、临时文件重命名等方式完成写入。Android 相册和文件提供方的 URI 不能简单当作普通路径处理。

建议保留共享的命名与冲突判断规则，为 Android 单独实现文件写入接口。

#### 4. 多语言和主题仍需核对

上一轮审查中，项目台账将英文界面标记为尚未完成。主题代码还使用了 Windows 专属的微软雅黑 UI 字体设置。

Android 可沿用主题配色并增加“跟随系统”，但应先核实语言资源的实际完成程度，不能假设全部语言资源已经具备。

### 3.3 当前导出上限

上一轮审查指出，`ExportOptions` 已设置最长边 **16,384 像素**、总像素约 **1.34 亿**的导出上限。

考虑到已确定 Android 与 Windows 导出能力对等，规划暂时保留此限制，不擅自放宽；P0/P1 阶段应核实其具体实现及在 Android 上的适用性。

## 四、推荐的开发路线图

### P0 · 完整代码审查与 Windows 基线确认

补齐完整源码检查，找出 Windows 专属依赖，记录当前可运行、可测试的状态。

**交付：** 完整模块清单、依赖关系、风险报告及测试基线。

### P1 · Android 核心技术验证

优先验证 HEIC 解码、高德地图、照片写入、高分辨率渲染等最容易遇到跨平台障碍的功能。

**交付：** 最小 Android 技术原型与可行性结论。

### P2 · 渐进式重构共享核心

在保持 Windows 正常工作的前提下，逐步分离业务逻辑与平台代码。成熟的改动通过测试后提前合并。

**交付：** 共享模块、平台接口、Windows 回归测试。

### P3 · Android Alpha

实现选择照片、加载预设、正确预览和 JPG/PNG 导出的完整基础流程。

**交付：** 首个能够实际处理照片的 Android APK。

### P4 · Android 编辑器与预设互通

加入非结构性属性编辑、逐张修改、撤销重做、资源替换和预设分享。

**交付：** 主要编辑功能和跨端预设互通能力。

### P5 · Android Beta

完成后台批量导出、系统分享、会话恢复、错误重试、日志和文件权限等平台集成功能。

**交付：** 通过 GitHub Pre-release 分发的 Beta APK。

### P6 · 验收与正式发布

多设备测试、Golden 图像比较、性能优化、自动化 CI、正式签名和发布验证。

**交付：** Android v1.0 与对应测试报告。

## 五、下一步建议

最值得优先执行的是 **P0：完整代码审查与 Windows 基线确认**，而不是直接开始制作 Android 界面。

本次已经完成需求规格、关键代码初审和分阶段实施计划；但完整依赖审计、实际编译、性能测量及真机验证仍未进行。后续需要在能够访问完整仓库和 Flutter 环境的开发环境中补齐这些证据，再确定具体修改哪些源文件。

**本次未修改任何 LumaCraft 源码、Git 分支、项目台账或 GitHub 配置。**

这样可以保留 Windows Beta 的稳定开发路线，同时让 Android 开发建立在经过验证的共享架构上。
